Suivi des demandes Codex - application reservation
===================================================

03/10/2026 - Contexte et travaux Kubernetes precedents
- L'application tourne dans le namespace app-reservation sur un cluster local Kubernetes: control plane 192.168.122.10, workers 192.168.122.11, .12 et .13.
- Services backend, frontend, PostgreSQL et Redis deja deployes. Le frontend est publie en NodePort 30080.
- Images construites avec Podman, puis chargees dans containerd sur les workers; Docker n'est pas necessaire.
- Metrics Server installe pour Kubernetes 1.31. Un contournement TLS kubelet (--kubelet-insecure-tls) a ete utilise uniquement pour ce cluster de laboratoire.
- HPA du backend configure entre 2 et 6 replicas, cible CPU 60%; une generation de charge a confirme le scale-up.
- La persistance PostgreSQL via PVC reste a planifier apres choix/installation d'un StorageClass et sauvegarde de la base existante.

03/10/2026 - Demande: parcours de reservation plus realiste
- Choix valide: inscription, connexion, deconnexion, sessions Redis avec TTL, panier Redis avec TTL, puis validation transactionnelle des billets dans PostgreSQL.
- Redis reste temporaire: commandes confirmees et stock ne sont jamais conserves uniquement dans Redis.
- L'utilisateur demande que les sources et fichiers de construction restent dans reservation-app sur le PC host pour conserver l'historique Git.
- L'utilisateur demande le maintien de ce journal date.

03/10/2026 - Implementation
- Backend Node/Express: comptes, hachage Argon2id, sessions Redis (30 min), paniers Redis (24 h), cookie HTTP-only, protection CSRF et limitation des tentatives d'authentification.
- PostgreSQL: tables utilisateurs, commandes et lignes de commande; decrement atomique du stock dans une transaction; cle d'idempotence du checkout; historique et annulation avec restitution du stock.
- Frontend: formulaire de connexion/inscription, bouton de deconnexion, ajout et edition des quantites du panier, validation et historique des commandes.
- Kubernetes: Redis protege par mot de passe, backend relie aux secrets, tags d'images 2.0; le Secret PostgreSQL existant n'est pas remplace.
- Secrets applicatifs generes dans Kubernetes et exclus de Git. Aucun PVC PostgreSQL n'est applique pendant cette evolution afin de ne pas risquer une migration destructive de la base existante.
- Les commandes de build/deploiement et limites connues sont documentees dans README.md.
- Dependances verrouillees dans package-lock.json; node_modules exclus du depot et le manifeste de secret PostgreSQL retire du suivi Git (son ancienne version reste dans l'historique Git initial).
- Images backend/frontend 2.0 construites avec Podman sur le control plane; archives copiees vers /tmp sur les trois workers. Validation Kubernetes --dry-run=server reussie et Secret reservation-app-secrets cree.
- Apres autorisation d'utiliser le mot de passe sudo fourni par l'utilisateur, images 2.0 importees dans containerd sur les trois workers et manifests Redis/backend/frontend appliques. PostgreSQL n'a pas ete redemarre ni remplace.
- Verifications apres deploiement: backend 2/2, frontend 2/2, Redis 1/1 Ready; `/api/auth/csrf` retourne HTTP 200. Les commandes de smoke test ne creent pas de compte ni de commande de test.
- Commit Git sur le host: c406f19 (Add Redis-backed accounts and transactional checkout). Le journal est conserve dans SuivieDemandeCodex.txt.
- Les quatre YAML initiaux du repertoire personnel du control plane sont archives dans `k8s/archive/control-plane-initial/`; la reference de secret PostgreSQL a remplace le mot de passe en clair.
- Les images binaires ne sont pas commitees dans Git. README explique l'usage d'un registre OCI pour les conserver et partager; les archives temporaires de build ne sont pas dans le depot.

03/10/2026 - Registre OCI local
- Registre Docker Distribution lance sur le control plane par une unite Podman Quadlet; demarrage au boot active avec linger utilisateur.
- Contenu du registre persiste dans le volume Podman `reservation-registry-data` (hors depot Git), accessible a `192.168.122.10:5000`.
- Images `reservation-backend:2.0` et `reservation-frontend:2.0` poussees dans le registre; manifests Kubernetes references maintenant ces noms.
- Acces local en HTTP sans authentification, limite au bind sur l'IP 192.168.122.10. Usage reserve au reseau de laboratoire; ne pas exposer tel quel a un reseau non fiable.
- Premier rollout a revele que containerd 2.2.1 ignorait les chemins `config_path` separes par deux-points pour les pulls CRI. Config corrigee vers `/etc/containerd/certs.d`, containerd redemarre sequentiellement sur les trois workers, avec verification `crictl pull` reussie. Le control plane est reste Ready et PostgreSQL/Redis sont restes Running.
- Rollout termine: backend 2/2, frontend 2/2; nodes Ready. `/api/health/ready` et `/api/auth/csrf` repondent HTTP 200.
- Configuration du registre et du client containerd documentee/versionnee sous `k8s/registry/`; instructions de build, push, deploiement et sauvegarde ajoutees au README.
- Les manifests ont d'abord rencontre `ErrImagePull` via le CRI; diagnostic confirme du config_path a deux chemins, correction et rollout final 2/2 reussi pour frontend/backend.
- Volume du registre exporte a l'arret puis importe en sauvegarde hors Git: `/dataSSD/K8S/registry-backups/reservation-registry-data-2026-10-03.tar` (86 MiB, SHA-256 `c48a8e4c89d38207e0f340578d70c8bc978b0a3f320f43f4431f62e8f09e0e12`). Registre redemarre et catalogue toujours disponible.
