Suivi des demandes Codex - application reservation
===================================================

03/10/2026 - Contexte et travaux Kubernetes precedents
- L'application tourne dans le namespace app-reservation sur un cluster local Kubernetes: control plane 192.168.122.10, workers 192.168.122.11, .12 et .13.
- Services backend, frontend, PostgreSQL et Redis deja deployes. Le frontend est publie en NodePort 30080.
- Images construites avec Podman, puis chargees dans containerd sur les workers; Docker n'est pas necessaire.
- Metrics Server installe pour Kubernetes 1.31. Un contournement TLS kubelet (--kubelet-insecure-tls) a ete utilise uniquement pour ce cluster de laboratoire.
- HPA du backend configure entre 2 et 6 replicas, cible CPU 60%; une generation de charge a confirme le scale-up.
- La persistance PostgreSQL via PVC reste a planifier apres choix/installation d'un StorageClass et sauvegarde de la base existante.

03/10/2026 - Demande: parcours de reservation plus realiste
- Choix valide: inscription, connexion, deconnexion, sessions Redis avec TTL, panier Redis avec TTL, puis validation transactionnelle des billets dans PostgreSQL.
- Redis reste temporaire: commandes confirmees et stock ne sont jamais conserves uniquement dans Redis.
- L'utilisateur demande que les sources et fichiers de construction restent dans reservation-app sur le PC host pour conserver l'historique Git.
- L'utilisateur demande le maintien de ce journal date.

03/10/2026 - Implementation
- Backend Node/Express: comptes, hachage Argon2id, sessions Redis (30 min), paniers Redis (24 h), cookie HTTP-only, protection CSRF et limitation des tentatives d'authentification.
- PostgreSQL: tables utilisateurs, commandes et lignes de commande; decrement atomique du stock dans une transaction; cle d'idempotence du checkout; historique et annulation avec restitution du stock.
- Frontend: formulaire de connexion/inscription, bouton de deconnexion, ajout et edition des quantites du panier, validation et historique des commandes.
- Kubernetes: Redis protege par mot de passe, backend relie aux secrets, tags d'images 2.0; le Secret PostgreSQL existant n'est pas remplace.
- Secrets applicatifs generes dans Kubernetes et exclus de Git. Aucun PVC PostgreSQL n'est applique pendant cette evolution afin de ne pas risquer une migration destructive de la base existante.
- Les commandes de build/deploiement et limites connues sont documentees dans README.md.
- Dependances verrouillees dans package-lock.json; node_modules exclus du depot et le manifeste de secret PostgreSQL retire du suivi Git (son ancienne version reste dans l'historique Git initial).
- Images backend/frontend 2.0 construites avec Podman sur le control plane; archives copiees vers /tmp sur les trois workers. Validation Kubernetes --dry-run=server reussie et Secret reservation-app-secrets cree.
- Apres autorisation d'utiliser le mot de passe sudo fourni par l'utilisateur, images 2.0 importees dans containerd sur les trois workers et manifests Redis/backend/frontend appliques. PostgreSQL n'a pas ete redemarre ni remplace.
- Verifications apres deploiement: backend 2/2, frontend 2/2, Redis 1/1 Ready; `/api/auth/csrf` retourne HTTP 200. Les commandes de smoke test ne creent pas de compte ni de commande de test.
- Commit Git sur le host: c406f19 (Add Redis-backed accounts and transactional checkout). Le journal est conserve dans SuivieDemandeCodex.txt.
- Les quatre YAML initiaux du repertoire personnel du control plane sont archives dans `k8s/archive/control-plane-initial/`; la reference de secret PostgreSQL a remplace le mot de passe en clair.
- Les images binaires ne sont pas commitees dans Git. README explique l'usage d'un registre OCI pour les conserver et partager; les archives temporaires de build ne sont pas dans le depot.

03/10/2026 - Registre OCI local
- Registre Docker Distribution lance sur le control plane par une unite Podman Quadlet; demarrage au boot active avec linger utilisateur.
- Contenu du registre persiste dans le volume Podman `reservation-registry-data` (hors depot Git), accessible a `192.168.122.10:5000`.
- Images `reservation-backend:2.0` et `reservation-frontend:2.0` poussees dans le registre; manifests Kubernetes references maintenant ces noms.
- Acces local en HTTP sans authentification, limite au bind sur l'IP 192.168.122.10. Usage reserve au reseau de laboratoire; ne pas exposer tel quel a un reseau non fiable.
- Premier rollout a revele que containerd 2.2.1 ignorait les chemins `config_path` separes par deux-points pour les pulls CRI. Config corrigee vers `/etc/containerd/certs.d`, containerd redemarre sequentiellement sur les trois workers, avec verification `crictl pull` reussie. Le control plane est reste Ready et PostgreSQL/Redis sont restes Running.
- Rollout termine: backend 2/2, frontend 2/2; nodes Ready. `/api/health/ready` et `/api/auth/csrf` repondent HTTP 200.
- Configuration du registre et du client containerd documentee/versionnee sous `k8s/registry/`; instructions de build, push, deploiement et sauvegarde ajoutees au README.
- Les manifests ont d'abord rencontre `ErrImagePull` via le CRI; diagnostic confirme du config_path a deux chemins, correction et rollout final 2/2 reussi pour frontend/backend.
- Volume du registre exporte a l'arret puis importe en sauvegarde hors Git: `/dataSSD/K8S/registry-backups/reservation-registry-data-2026-10-03.tar` (86 MiB, SHA-256 `c48a8e4c89d38207e0f340578d70c8bc978b0a3f320f43f4431f62e8f09e0e12`). Registre redemarre et catalogue toujours disponible.

03/10/2026 - PostgreSQL sur NFS
- Le control plane a un PV NFS `postgres-pv-nfs` de 5Gi (serveur 192.168.122.1, export /dataSSD/K8S/nfs-postgres), lie au PVC `postgres-pvc` en ReadWriteMany. Le nom observe dans Kubernetes est `postgres-pv-nfs` (pas `nfs-storage`).
- Le Deployment PostgreSQL initial etait sans PVC, avec une strategie RollingUpdate et des identifiants en clair; un Secret `reservation-db-credentials` existe et ses identifiants ont ete verifies identiques aux valeurs actives sans les afficher.
- Avant migration, dump custom PostgreSQL valide, conserve hors Git sur le control plane: `~/reservation-db-before-nfs-20261003.dump`. La migration arrete momentanement le HPA/backend pour figer les ecritures, puis restaure les donnees sur le PVC NFS.
- Nouveau `k8s/postgres.yaml`: PVC monte sur PGDATA, une seule replique, strategie Recreate pour eviter deux instances partageant le meme repertoire, sondes PostgreSQL, ressources bornees, identifiants fournis par Secret. Le Service PostgreSQL est conserve.
- Dossier exporte vide avant migration, permissions definies en UID/GID 70:70 mode 0700; un Pod de test non-root a valide ecriture/suppression via le PVC. L'export NFS du laboratoire est `no_root_squash`, a garder sur reseau isole.
- Backend et HPA suspendus pendant l'export final/restauration puis remis en service. PostgreSQL Ready sur le PVC, cinq tables restaurees, quatre evenements presents; backend 2/2 et `/health/ready` retourne 200.
- Test de reprise: worker3 cordonne, Pod PostgreSQL supprime proprement puis reprogramme sur worker1 via le meme PVC NFS; quatre evenements encore presents. Worker3 remis schedulable. Pendant le bref arret DB, les Pods backend ont redemarre sur connexion refusee puis sont redevenus Ready apres retour PostgreSQL.
- Les YAML autonomes obsoletes `~/backend.yaml`, `~/frontend.yaml`, `~/postgres.yaml` et `~/redis.yaml` etaient identiques aux snapshots archives sauf le PostgreSQL assaini; ils ont ete supprimes du control plane. Dump de secours conserve hors Git sous `~/reservation-db-before-nfs-20261003.dump`.
- Limites: NFS permet la reprogrammation sur un autre worker, mais le serveur NFS reste un point de panne; RWX n'autorise pas plusieurs serveurs PostgreSQL concurrents sur le meme PGDATA.

03/10/2026 - Consolidation des sources host/control plane
- Le depot Git faisant autorite reste `/dataSSD/K8S/reservation-app` sur le host; les deux dossiers du control plane n'etaient pas des clones Git.
- `~/reservation-app-v2` contenait les sources applicatives actuelles identiques au depot, mais n'avait pas les derniers manifests PostgreSQL/NFS et l'archive; `~/reservation-app` etait une copie applicative plus ancienne.
- Synchronisation du depot host vers `~/reservation-app` (exclusions: `.git`, secrets Kubernetes, fichiers `.env`, node_modules, sauvegardes); comparaison rsync sans difference apres transfert.
- Suppression de `~/reservation-app-v2` et de l'ancien `~/reservation-app/k8s/database-secret.yaml` ignore par Git. Il ne reste qu'un dossier clair sur le control plane: `~/reservation-app`, miroir de travail du depot host.
- README corrige pour que les commandes de build, push et deploiement utilisent uniquement `~/reservation-app`. Le depot Git du host garde seul l'historique; le repertoire distant n'est pas un clone Git.

03/10/2026 - Repartition, acces stable et tolerance aux pannes
- HAProxy installe sur le host PC; configuration versionnee dans `ops/haproxy/`, liee uniquement a `192.168.122.1:8080` (passerelle libvirt du reseau VM), avec health checks sur les NodePort workers `.11/.12/.13:30080`. Le LAN n'est pas expose.
- Frontend et backend passent a 3 replicas initiaux, repartis entre workers; tolerations `not-ready` et `unreachable` de ces composants sans etat reduites a 30 secondes. PostgreSQL conserve le delai Kubernetes par defaut pour eviter le risque de deux processus sur le meme volume NFS apres partition.
- HPA backend conserve max 6 et cible CPU 60%, minReplicas releve a 3. Backend demarre sans attendre PostgreSQL/Redis, retente PostgreSQL avec backoff exponentiel borne; Redis conserve sa reconnexion native et un retry initial.
- En panne DB, apres chargement initial du catalogue, `/api/events` sert son dernier instantane en lecture seule et le frontend affiche un bandeau. Authentification, panier et commandes restent indisponibles; aucune reservation n'est confirmee hors PostgreSQL. Readiness autorise le mode degrade seulement avec cache catalogue et Redis pret.
- Tests node:test ajoutent la couverture des retries et de leur annulation. Outils host ajoutes: `scripts/load-test.mjs` pour charge concurrente/HPA, `scripts/simulate-frontend-failure.sh` pour cordon, suppression et remplacement d'un pod frontend seulement, puis uncordon.
- Images backend/frontend 2.1 construites avec Podman puis poussees dans le registre; rollout initial valide. Le test de panne DB a revele qu'une erreur `57P01` emise par une connexion PostgreSQL idle non geree faisait quitter Node. Listener `pool.on('error')` ajoute, images 2.2 construites/poussees, dry-run serveur et rollouts valides.
- Charge host sur 2.1, 60 clients pendant 180 s: 141761 requetes, 141761 HTTP OK, 0 erreur, 787.3 req/s, latence moyenne 76 ms, p95 292 ms. HPA est passe de 3 a 5 puis 6 replicas; apres arret, CPU retombe a 2%, et le HPA reduit graduellement (120 s de stabilisation, un pod/minute).
- Validation du mode degrade sur 2.2: suppression gracieuse du Pod PostgreSQL; `/api/events` a repondu HTTP 200 avec `X-Service-State: degraded`, les trois backend Pods sont restes Running sans redemarrage, PostgreSQL a retrouve Ready avec son PVC NFS et le catalogue est revenu au mode normal. Aucune ecriture ni commande n'a ete faite pendant ce test.
- Panne simulee: pod frontend supprime pendant cordon de worker1, recreation sur worker2, endpoint HAProxy reste joignable; deuxieme passage a place un pod sur worker3. Backend egalement reprogramme sans interruption sur worker2 pendant cordon de worker1. Workers tous uncordoned/Ready; etat final a 3 frontend + 3 backend Ready, un par worker, PostgreSQL 1/1 et Redis 1/1.

03/10/2026 - Test de forte charge, mesures et reglage CPU/probes
- Campagne pilote host: 500 clients, 100 s, GET `/api/events`; collecteur surveille toutes les 5 s HPA, CPU/memoire par pod et noeud, Ready/restarts/placement; collecte finale des evenements, logs frontend/backend et `cpu.stat` cgroup.
- Passage 1 (HPA max6, backend limit300m): 77367 reponses 200, 0 erreur, 757.3 req/s, moyenne 651ms, p95 2181ms. Les backends atteignaient 300m; evenements de timeouts probes a 1s observes dans les evenements.
- Passage 2 (HPA max9, probes 3s, frontend limit250m, backend encore a 300m): 66287 reponses 200, 0 erreur, 644.7 req/s, moyenne 762ms, p95 2442ms. Le HPA n'a atteint 9 que tard pendant le test; les pods de scale-up refroidissaient encore.
- `cpu.stat` confirmait un throttling backend significatif (exemple: 388 periodes sur 443). Le host et les noeuds n'etaient pas a court de memoire; les VM workers ont 2 CPU chacune. Limite backend augmentee de 300m a 400m; HPA garde max9 car le worker le plus charge a approche 90% CPU.
- Passage 3 apres reglage: 101606 reponses 200, 0 erreur, 1005.7 req/s, moyenne 493ms, p95 2131ms. HPA 3->9, tous les pods backend Ready sans redemarrage a la fin; tous les workers Ready. Aucun timeout liveness/readiness pendant cette derniere charge; les evenements `connection refused` concernent les premieres sondes startup des pods fraichement crees.
- A 9 pods, HPA affiche encore une utilisation superieure a la cible CPU de 60% et `ScalingLimited: TooManyReplicas`; un worker a culmine a 90% CPU, memoire worker max38%, PostgreSQL max observe 473m CPU/175Mi. `cpu.stat` final indique encore environ 57.8% de periodes throttlees agreges: charge soutenue proche de la capacite CPU; ne pas augmenter le max replicas sans nouveau test de capacite et surveillance node.
- Resultats detailles conserves hors Git dans `/tmp/reservation-load-20261003-222741`, `/tmp/reservation-load-20261003-223223` et `/tmp/reservation-load-20261003-223655`. Procedure reproductible de lancement/observation dans `TestsInjectionEtSurveillance.txt`.

03/10/2026 - Extension de l'injecteur au parcours de reservation
- `scripts/load-test.mjs` conserve le scenario `catalog` (GET `/api/events`) et ajoute `SCENARIO=booking`: un pool fixe d'utilisateurs distincts s'authentifie une fois puis enchaine catalogue, ajout/lecture du panier Redis, checkout transactionnel PostgreSQL, annulation et verification de l'historique. Les cookies/CSRF sont geres par virtual user; echec journalise par etape et tentative de nettoyage du panier/annulation en recuperation.
- Le pool est etendu a 500 comptes reutilisables, provisionnes par petits lots pour limiter la pression Argon2. Le backend expose `AUTH_RATE_LIMIT` avec valeur par defaut 10; le lanceur la releve temporairement a 1000 pour bootstrap/login puis restaure la valeur precedente meme lors d'une interruption.
- Mot de passe aleatoire du pool conserve hors Git dans le fichier local de configuration utilisateur en mode 0600. Les 500 comptes restent en base; le nettoyage restitue le stock et supprime uniquement l'historique des commandes du pool de test.
- Test reel 500 VU/100 s sur backend 2.4: 1 931 parcours OK et 2 429 echecs; diagnostic d'epuisement des pools PostgreSQL car checkout conservait un client durant `loadOrder()`.
- Correction: checkout libere maintenant le client au commit avant la relecture de commande. Image 2.5 publiee dans le registre local et deployee. Nouveau test: 10 127 parcours completes, 0 erreur, 98.08 parcours/s, p95 7.548 s; HPA 3->9, CPU worker max 92%, memoire worker max 40%, sans restart backend. `AUTH_RATE_LIMIT=10` restaure; 500 comptes conserves, commandes de test nettoyees.
- Commande et mesures detaillees, y compris le passage initial rate et les diagnostics: `TestsInjectionEtSurveillance.txt`; resultats bruts hors Git dans `/tmp/reservation-load-20261003-234625` et `/tmp/reservation-load-20261003-235117`.
